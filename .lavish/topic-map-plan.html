Year filter, animated transitions and timeline mode

The goal: filter the map by year and switch to a chronological layout, with dots flying smoothly between positions instead of jumping, on desktop and on a phone.

This is already on main. Commit 65a8e13 (2026-08-30) added both modes, the year chips, CSS-driven transitions and the pure layout module lib/mapLayout.ts. So this plan compares that implementation with the alternatives, confirms where the layout should be calculated, and lists what is still missing. I'm not proposing a rewrite.

Target behavior

One set of 253 <circle>s, each keyed by post id. Changing a control only changes where each dot sits and whether it's visible.

Approaches compared

The decision is how to render the dots and how to animate them. 253 dots is small, so headroom up to ~2k matters more than raw speed.

A · SVG + CSS transitions on --map-x/--map-ycurrent Low. No animation library. React sets two custom properties per dot and the browser interpolates. One React commit per change, then zero JS per frame. Fine to ~1.5k. The blur glow is the only expensive part and it's hidden during the flight. Native hit-testing, a 5-unit invisible stroke for a fat tap target, tap opens the modal. Supports prefers-reduced-motion. Free: CSS retargets from the current computed transform.
B · SVG + JS tweenframer-motion / react-spring / d3-transition Medium. Adds a dependency (~30–50 kB for motion). Springs feel nice, but every dot becomes a motion component. Writes attributes on the main thread every frame (253 × 60/s). OK on desktop, can jank on mid-range Android around 1k dots. Same SVG hit-testing as A. Springs keep velocity, which is slightly nicer than A.
C · Canvas 2D + rAF interpolation High. Needs manual hit-testing (quadtree), DPR scaling, a hover/focus layer, and redrawn axes and labels. The SVG a11y is lost. Best headroom (10k+). Overkill at 253. Taps need custom hit radii and the canvas has to be resized on rotation. Easy, since you own the loop.
D · WebGLregl / pixi / deck.gl Very high, with a 100–400 kB library for a decorative section. 100k+ dots. Irrelevant here. Context loss and battery cost, and text labels still need DOM. Shader uniforms.
E · FLIP / View Transitions API Medium. 253 view-transition-names, or measuring each dot's position before and after. View Transitions snapshot elements as bitmaps, so dots blur when the zoom changes. FLIP needs a layout read per dot. View Transitions only recently reached Safari, and SVG children are poorly supported. A new transition cancels the running one and the dots snap.

Verdict: keep A. It's the simplest option that stays smooth when someone clicks through the year chips quickly. The layout function doesn't know about the renderer, so moving to canvas later (C) would only replace DotLayer.

Architecture: where each calculation runs

The work is split into three tiers by cost and by what each step depends on.

Offline pipeline

Anything that depends on content

Embeddings, the LLM taxonomy and UMAP are slow and nondeterministic, so they belong here. Don't precompute the timeline beeswarm in the pipeline, because it depends on screen orientation and on the selected year range.

Client, pure function

Anything that depends on the view

Mode, year and orientation give 2 × 6 × 2 = 24 possible layouts, each under 0.2 ms. A Web Worker or an API route would cost more in overhead than the calculation itself. The same function runs during SSR, so the first paint already has the right positions and nothing flashes.

Browser compositor

Everything between keyframes

Interpolation, the stagger (index × 0.5 ms, capped at 120 ms) and fading. React renders once per click, and hover and modal state live outside the memoized dot layer.

The timeline beeswarm is O(n²) within each lane (done.some(...) scans every dot already placed). It doesn't matter at today's size, but at about 2k posts it would take roughly 20 ms on a phone. Scanning only a sliding window of dots within minGap would make it close to linear.

Animation choreography

Already implemented.

  • Exits fade in place. In timeline mode, filtered-out dots park at their lane center instead of flying across the screen.
  • Stagger only while moving. The .is-moving class lasts 720 ms, so hover isn't delayed.
  • Glow off during flight. feGaussianBlur re-renders every frame and is the real 60 fps bottleneck on phones.
  • Cluster labels move to the centroid of their topic's visible dots and are pushed apart vertically so they don't overlap.
  • Reduced motion turns off all transitions and the stagger.

Mobile

≤640 px, checked against TopicMap.tsx.

  • Vertical timeline (viewBox 100×170). Eight horizontal lanes would be about 4 px tall each at 390 px wide.
  • Orientation comes from useSyncExternalStore(matchMedia), with 'h' on the server, so phones get a single client re-render after hydration.
  • Tap targets: a dot has r = 1.05 plus a transparent stroke of 5, about 20 px on a phone.
  • Year chips and the legend scroll horizontally, and tapping a dot opens the modal because touch has no hover.

Proposed follow-ups

Small and independent, in priority order.

  1. Keep mode and year in the URL

    Sync ?map=timeline&year=2024 with history.replaceState and read it on load, so a specific view can be shared. Don't use Next router navigation, because it would re-run the RSC payload with every post in it.

Risks and open questions

Did you want something beyond what's shipped?

If the current behavior is what you had in mind, this is a review and only the follow-ups are new. If you wanted a different timeline (for example one row of all posts colored by topic, or a month histogram), annotate the timeline mockup above.

Should the year filter zoom?

Right now, picking a year rescales the map to fit that year's posts (up to 2.2×). The alternative keeps the map fixed and only fades other years, which makes comparing years easier but leaves sparse years (2022 has 35 posts) looking empty.

Pipeline reruns change the UMAP

Regenerating map.json moves every dot, which is expected. Positions in the timeline depend only on dates, so they stay stable.
